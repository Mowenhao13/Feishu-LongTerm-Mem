# DeerFlow沙箱机制

## DeerFlow沙箱机制

DeerFlow 的沙箱机制（Sandbox System）为智能体提供了一个隔离的执行环境，使其能够安全地运行 shell 命令和管理文件。多智能体协作通过**共享 thread\_id** 来实现对同一个沙箱实例的并发访问和状态同步。

---

## 沙箱机制核心原理

DeerFlow 的沙箱架构基于 SandboxProvider 抽象接口，支持多种运行模式：

### 运行模式与隔离级别

- **本地模式 \(****LocalSandboxProvider****\)**: 直接在宿主机文件系统运行，通过路径映射（Path Mapping）限制访问范围，主要用于受信任的本地开发 \[1\]\(\#3\-0\) 。

- **容器模式 \(****AioSandboxProvider****\)**: 基于 Docker 或 K8s，为每个会话提供完全隔离的容器环境。它是生产环境的推荐模式 \[2\]\(\#3\-1\) 。

### 确定性沙箱 ID 与生命周期

沙箱的 ID 是根据 thread\_id 确定性生成的 \[3\]\(\#3\-2\) 。

- **获取 \(****acquire****\)**: SandboxMiddleware 在智能体运行前根据当前线程 ID 获取沙箱 \[4\]\(\#3\-3\) 。

- **复用**: 沙箱在同一线程的多次对话（Turns）中会被复用，并存放在“温池”（Warm Pool）中以减少冷启动开销 \[5\]\(\#3\-4\) 。

### 虚拟路径映射

智能体操作的是虚拟路径（如 /mnt/user\-data/workspace），系统会将其透明地转换为宿主机上与该线程绑定的物理路径 \[6\]\(\#3\-5\) 。



---

## 多智能体如何操作沙箱

在 DeerFlow 中，lead\_agent（主智能体）和通过 task\(\) 工具拉起的 sub\-agents（子智能体）可以共同操作沙箱：

### 共享沙箱环境

由于沙箱 ID 是由 thread\_id 派生的，只要多个智能体处于同一个会话线程中，它们通过 ensure\_sandbox\_initialized 获取到的将是同一个沙箱实例 \[7\]\(\#3\-6\) 。这使得子智能体可以读取主智能体上传的文件，或者为主智能体生成输出。

### 并发安全与锁定

为了防止多个智能体同时操作同一个沙箱导致冲突（例如同时修改同一个文件），系统实现了两层锁定机制：

- **进程内锁定**: 使用 threading\.Lock 确保同一进程内的多个线程序列化访问特定沙箱 \[8\]\(\#3\-7\) 。

- **跨进程锁定**: 在获取沙箱时使用文件锁（File Lock），确保多个实例（如 K8s 中的不同 Pod）不会重复创建同名容器 \[9\]\(\#3\-8\) 。

### 隔离的 ACP 工作区

虽然基础文件系统是共享的，但每个线程都有独立的 acp\-workspace（用于 ACP 插件），该目录在沙箱内通常是只读的，以保证执行结果的不可篡改性 \[10\]\(\#3\-9\) 。
