The Memory Sync system is responsible for the "Write" path of the search infrastructure. While MongoDB serves as the primary source of truth for all memory entities, high-performance retrieval requires these entities to be synchronized to **Elasticsearch** (for BM25 keyword search) and **Milvus** (for vector similarity search).

## MemorySyncService

The `MemorySyncService`[src/biz_layer/mem_sync.py47-48](https://github.com/EverMind-AI/EverOS/blob/d40b8703/src/biz_layer/mem_sync.py#L47-L48) is the central orchestrator for synchronizing extracted memories. It ensures that once a memory (Episode, Foresight, Atomic Fact, Agent Case, or Agent Skill) is persisted in MongoDB and vectorized, it is correctly indexed in the search backends.

### Key Responsibilities

- **Data Normalization**: Converts MongoDB document formats into search-engine-compatible models using specialized converters [src/biz_layer/mem_sync.py81-94](https://github.com/EverMind-AI/EverOS/blob/d40b8703/src/biz_layer/mem_sync.py#L81-L94)
- **Dual-Write Orchestration**: Manages the logic for writing to both Milvus and Elasticsearch, with options to toggle either backend independently [src/biz_layer/mem_sync.py99-100](https://github.com/EverMind-AI/EverOS/blob/d40b8703/src/biz_layer/mem_sync.py#L99-L100)
- **Batch Operations**: Supports high-throughput synchronization for large sets of records, such as those generated during a full-history extraction or re-indexing [src/biz_layer/mem_sync.py206-218](https://github.com/EverMind-AI/EverOS/blob/d40b8703/src/biz_layer/mem_sync.py#L206-L218)

## Converters and Tokenization

Search backends require specific data transformations. The system uses a "Converter" pattern to separate business logic from infrastructure-specific schemas.

### Elasticsearch Converters (BM25)

Elasticsearch repositories rely on text fields for keyword matching.

- **Jieba Tokenization**: For Chinese content, the converters (e.g., `ForesightConverter`, `EventLogConverter`) are responsible for pre-tokenizing text before it reaches ES to ensure accurate BM25 scoring [src/biz_layer/mem_sync.py132-133](https://github.com/EverMind-AI/EverOS/blob/d40b8703/src/biz_layer/mem_sync.py#L132-L133)
- **Search Content Construction**: Multiple fields (title, summary, content) are often concatenated into a single `search_content` field which uses the `standard` analyzer or custom tokenizers [src/infra_layer/adapters/out/search/elasticsearch/memory/episodic_memory.py82-105](https://github.com/EverMind-AI/EverOS/blob/d40b8703/src/infra_layer/adapters/out/search/elasticsearch/memory/episodic_memory.py#L82-L105)

### Milvus Converters (Vector)

Milvus converters prepare entities for vector insertion.

- **Vector Mapping**: Maps the `vector` field from MongoDB (generated by the embedding service) to the Milvus `FLOAT_VECTOR` field [src/infra_layer/adapters/out/search/repository/event_log_milvus_repository.py101-103](https://github.com/EverMind-AI/EverOS/blob/d40b8703/src/infra_layer/adapters/out/search/repository/event_log_milvus_repository.py#L101-L103)
- **Metadata Serialization**: Since Milvus is primarily a vector database, non-searchable metadata is often serialized into a JSON string to be stored in a `metadata` VARCHAR field for retrieval [src/infra_layer/adapters/out/search/repository/event_log_milvus_repository.py112-113](https://github.com/EverMind-AI/EverOS/blob/d40b8703/src/infra_layer/adapters/out/search/repository/event_log_milvus_repository.py#L112-L113)

## Implementation Detail: Milvus Indexing

Milvus collections are managed via repository classes that extend `BaseMilvusRepository`. To handle the synchronous nature of the underlying `pymilvus` library without blocking the asyncio event loop, EverOS uses `AsyncCollection`[src/core/oxm/milvus/async_collection.py51-58](https://github.com/EverMind-AI/EverOS/blob/d40b8703/src/core/oxm/milvus/async_collection.py#L51-L58) This class wraps blocking calls in a dedicated thread pool `_milvus_executor`[src/core/oxm/milvus/async_collection.py14-25](https://github.com/EverMind-AI/EverOS/blob/d40b8703/src/core/oxm/milvus/async_collection.py#L14-L25)

## Batch Synchronization

When large amounts of data are processed (e.g., re-indexing or initial ingestion), `MemorySyncService` provides batch methods to minimize I/O overhead and network latency.

1. **Extraction**: Records are fetched from MongoDB via their respective raw repositories. For example, `AgentSkillRawRepository` provides `find_by_ids` for batch fetching using `build_id_filter` to handle both `ObjectId` and raw strings [src/infra_layer/adapters/out/persistence/repository/agent_skill_raw_repository.py35-53](https://github.com/EverMind-AI/EverOS/blob/d40b8703/src/infra_layer/adapters/out/persistence/repository/agent_skill_raw_repository.py#L35-L53)[src/core/oxm/mongo/mongo_utils.py48-62](https://github.com/EverMind-AI/EverOS/blob/d40b8703/src/core/oxm/mongo/mongo_utils.py#L48-L62)
2. **Filtering**: Records without valid vectors are discarded to prevent search backend errors during indexing [src/biz_layer/mem_sync.py116-120](https://github.com/EverMind-AI/EverOS/blob/d40b8703/src/biz_layer/mem_sync.py#L116-L120)
3. **Conversion**: Records are transformed using converters like `ForesightMilvusConverter` or `EventLogConverter`[src/biz_layer/mem_sync.py125-133](https://github.com/EverMind-AI/EverOS/blob/d40b8703/src/biz_layer/mem_sync.py#L125-L133)
4. **Insertion**:

- **Milvus**: Uses `insert` via `AsyncCollection`[src/core/oxm/milvus/async_collection.py85-95](https://github.com/EverMind-AI/EverOS/blob/d40b8703/src/core/oxm/milvus/async_collection.py#L85-L95) In batch modes, `flush=False` is often preferred to allow Milvus to manage data persistence asynchronously [src/biz_layer/mem_sync.py126](https://github.com/EverMind-AI/EverOS/blob/d40b8703/src/biz_layer/mem_sync.py#L126-L126)
- **Elasticsearch**: Uses repository `create` methods which wrap the underlying ES DSL `save()`[src/infra_layer/adapters/out/search/repository/event_log_es_repository.py151-152](https://github.com/EverMind-AI/EverOS/blob/d40b8703/src/infra_layer/adapters/out/search/repository/event_log_es_repository.py#L151-L152)
