# 全量原始对话 → LLM 直接问答实验设计

> 验证目的：对比"全量原始对话直接喂给 LLM"与"预处理管线（提取 → 存图 → MCP 查询 → 回答）"两种模式下 LLM 的回答准确率。
>
> 触发条件：owner wenhao Mo 要求验证当前预处理管线的必要性。

---

## 1. 实验数据集

### 数据源

**主数据集**：`memory_stores/eval_test_full`

| 指标 | 值 |
|------|----|
| Episode 数量 | 15 |
| 原始消息条数 | 269 |
| 字符数（中文） | ~6,889 |
| 估算 Token 数 | ~3,500（中文按 2 字/token） |
| Decision 分支 | 28（但仅 5 个有提取的 .md 文件） |
| Topic 数量 | 1（全部属于 `general`） |

### 输入格式

所有 15 个 Episode 的 `original_data` 按时间序拼接，格式如下：

```
=== Episode: ep_xxxxxx (timestamp: 2026-07-29T17:37:01Z) ===

消息队列设置消息保留策略
容器资源预留
消息队列Topic设计
消息队列Topic命名规范
容器先搭1主2从
消息队列Rebalance
消息队列消息体大小限制

=== Episode: ep_yyyyyy (timestamp: 2026-07-29T17:37:03Z) ===

消息队列还是Kafka好
容器选K8s就对了

...
```

**不做的处理**：
- 不做去重（ep_b55c154b6 存在大量重复消息，保留原始状态）
- 不做结构化提取（决策、实体、关系都不标注）
- 不做消息分组（不区分"决策消息"和"非决策消息"）

**为什么不做去重？** 重复是原始对话的自然特征。预处理管线的优势之一就是去重——如果原始模式因为重复消息而表现差，那本身就是一个有效结论。

## 2. 测试问题集

### 问题选择原则

1. **答案完全存在于原始消息中**——所有事实都在聊天记录里被明确提及
2. **覆盖多维度**：单 Episode 检索 / 跨 Episode 关联 / 数值精确性 / 对比推理
3. **难度分级**：简单（显式陈述）→ 中等（需关联）→ 较难（跨 session + 数值精确）
4. **对应现有决策提取结果**：每个问题都对应一条或多条已提取的 Decision 分支

### 问题列表

| # | 问题 | 答案 | 来源 Episode | 难度 | 对应 Decision |
|---|------|------|-------------|------|---------------|
| 1 | 数据库方面，后端选用了什么数据库？ | PostgreSQL（PG） | ep_b55c154b6（显式多次） | 简单 | 决策文件中有"数据库用PG" |
| 2 | 团队决定使用什么消息队列？ | Kafka | ep_b55c154b6（显式多次） | 简单 | 消息队列消息压缩、Kafka高可用等 |
| 3 | 容器平台选择了什么方案？ | Kubernetes（K8s） | ep_b55c154b6（显式"容器化就用K8s"） | 简单 | 多个 K8s 相关决策 |
| 4 | 前端技术栈的决定是什么？ | React + Next.js + TypeScript + Vite | ep_b55c154b6、ep_a7b1155b5 | 简单 | 多处提及 |
| 5 | 数据库的索引使用有什么规则或注意事项？ | 避免过多索引导致写入变慢 | ep_b7987b51a | 中等 | 无对应决策文件（LLM 未提取此条） |
| 6 | 数据库迁移工具选择了什么？原因是什么？ | sqitch，版本控制、回滚方便 | ep_8b80ff7eb | 中等（需关联） | 对应决策分支 |

| 8 | 关于"死锁检测"团队有什么具体决定吗？ | 有人提出"好像还有一个数据库死锁检测的问题"，但没有记录后续决定 | ep_b7987b51a | 中等（需要分辨"提到了"vs"决定了"） | 无对应决策——这是一个"讨论但未决定"的测试点 |
| 9 | SLA方面，核心链路和非核心链路的SLO分别是什么？ | 核心支付链路 99.99%，一般业务 99.9%，内部工具 99% | ep_aa7f8402a | 较难（数值精确性） | 对应"SLA和SLO"相关决策 |
| 10 | 团队对数据库选型的最终决策和备选方案的对比是什么？ | 最终选 PG。备选对比：PG vs MySQL，PG OLTP性能更好、扩展性更强（JSONB、GIS、timescaledb）、RDS性价比好，但学习成本高 | ep_b55c154b6（跨多条消息的推理） | 较难（跨消息推理 + 对比分析） | 多处 PG 决策 |

### 📝 关键标注

- **Q5 和 Q8 是陷阱题**：Q5 只是"提到"了索引注意事项但没有形成结构化 Decision；Q8 只是"有人提出"死锁检测话题但无后续。这两个问题用于验证 LLM 能否区分"对话中提到"和"作出了决定"。
- **Q10 是综合题**：没有单一消息说"最终选了 PG 因为...PK 了 MySQL..."，答案散布在 ~15 条不同消息中，需要跨消息关联推理。

## 3. 评分标准细则

### 评分等级

| 等级 | 分数 | 判定标准 |
|------|------|---------|
| **完全正确** | 2 | 答案包含所有关键信息，无事实错误 |
| **部分正确** | 1 | 答案包含部分正确信息，但遗漏关键点或包含无关/错误信息 |
| **错误/未知** | 0 | 答案核心事实错误，或回答"不知道" |

### 各题评分指南

**Q1（数据库选型）**：
- 完全正确：明确回答"PostgreSQL/PG"
- 部分正确：回答"关系型数据库"/"RDS"但未说 PG
- 错误：回答 MySQL/其他

**Q2（消息队列）**：
- 完全正确：回答"Kafka"
- 部分正确：回答"消息队列"但未具名
- 错误：回答 RabbitMQ/其他

**Q3（容器平台）**：
- 完全正确：回答"Kubernetes/K8s"
- 部分正确：回答"容器化方案"但未具名
- 错误：回答 Docker Swarm/其他

**Q4（前端技术栈）**：
- 完全正确：至少说出 React + Next.js + TypeScript（三个核心）或 React + Vite
- 部分正确：只说"React"但未提及框架和语言
- 错误：回答 Vue/Angular/其他

**Q5（索引规则）**：
- 完全正确：回答"避免过多索引导致写入变慢"
- 部分正确：回答"要建索引"但未提及性能权衡
- 错误：回答具体索引类型/策略

**Q6（迁移工具 + 原因）**：
- 完全正确：回答"sqitch，因为版本控制好、回滚方便"
- 部分正确：只说"sqitch"没说原因，或只说原因没说是 sqitch
- 错误：回答 Flyway/Liquibase/其他

**Q7（资源限制策略）**：
- 完全正确：提到 ResourceQuota + LimitRange 两层配合 + CPU 超卖 1:2 内存不超卖
- 部分正确：只说其中一部分
- 错误：答案错误

**Q8（死锁检测）**：
- 完全正确：回答"有人提到了但无明确决定"
- 部分正确：说"有死锁检测"（过于肯定）或"没提过"（遗漏）
- 错误：杜撰了一个决策

**Q9（SLO 数值）**：
- 完全正确：精确说出三个数值（99.99%/99.9%/99%）
- 部分正确：答对部分数值或只说"四九、三九"
- 错误：数值错误

**Q10（DB 选型对比）**：
- 完全正确：说出最终选 PG + 至少 2 个对比点（如 OLTP 性能、扩展性、RDS、学习成本）
- 部分正确：只说最终选 PG 但对比分析不足
- 错误：说选 MySQL 或其他

## 4. 实验执行方案

### 原始模式（实验组）

**Prompt 结构**：

```
你是一个技术决策回答助手。以下是团队在架构讨论中的全部聊天记录。
请根据聊天记录回答后面的问题。

聊天记录：
{拼接后的全部 15 个 Episode 消息}

---

问题：
{10 个问题的完整列表，每行一个，编号 1-10}
```

**参数建议**（wenhao Mo 根据可用模型调整）：
- Model: Claude Sonnet / GPT-4o-mini（选一个稳定的即可，重点是在同一模型上对比）
- Temperature: 0（确保可复现性，避免随机性干扰）
- Max tokens: 合理上限（答案不会很长）
- 重复次数：3 次（取众数，消除偶发不一致）
- 是否提供问题列表：一次性全问（模拟真实使用场景中的全量查询）

### 预处理模式（对照组）

**输入**：现有 MemoryGraph + Decision 分支中的信息（28 条 decision 的 summary + content）
**Prompt 结构**：

```
以下是从聊天记录中提取的结构化决策信息：
{每条 decision 的 summary + content}

问题：
{10 个问题}
```

**注意**：预处理模式中 LLM 可能因为看不到原始上下文而丢失细节。如果预处理模式表现差——例如 Q5/Q8（原始对话中有但 LLM 未提取为 Decision）——那正好论证了"提取管线有遗漏"。

## 5. 结论模板

### 场景 A：原始模式 ≈ 预处理模式（或原始模式更好）

```
结论：当前 ~3.5K token 的数据规模下，全量对话直接喂给 LLM 的准确率不低于当前预处理管线。
推论：在数据规模达到 ~100K token 之前，预处理管线的价值不大。
建议：先将 80% 的提取投入用于提升 retrieval 覆盖率（而非准确率），
等到单次对话上下文超过 100K tokens 时再优化提取管线。
```

### 场景 B：预处理模式明显更好（原始模式 < 60%）

```
结论：即使 ~3.5K token 的数据规模，当前预处理管线仍然为 LLM 提供了结构化检索优势。
关键差距：______（如"数值精确题"或"跨消息推理题"）
建议：维持现有预处理管线架构，但在 Phase A 的 MemoryGraph 优化中
确保预处理的数据质量（修复 Q5/Q8 这类遗漏问题）。
```

### 场景 C：两者表现都不好（都在 50% 以下）

```
结论：不是存储模式的问题，而是 LLM 本身对这类技术决策溯源任务识别能力不足。
建议：引入 Few-shot 示例 + 更精细的 prompt 工程，
在提升 prompt 质量后再重新评估两种模式。
额外检查：确认问题是否超出了 LLM 的上下文窗口限制（~3.5K tokens 不应）。
```

## 6. 执行指南

### 手动执行步骤（wenhao Mo）

1. **准备输入文件**：执行以下脚本生成实验 prompt
   ```python
   # scripts/prepare_raw_experiment.py
   import json
   
   with open('memory_stores/eval_test_full/hypergraph/state.json') as f:
       data = json.load(f)
   
   # 按时间序拼接所有消息
   episodes = sorted(
       data['episodes'].values(),
       key=lambda e: e.get('timestamp', '')
   )
   
   lines = []
   for ep in episodes:
       lines.append(f"=== Episode: {ep['id']} (timestamp: {ep.get('timestamp', '')}) ===")
       lines.append("")
       for msg in ep.get('original_data', []):
           lines.append(msg.get('content', ''))
       lines.append("")
   
   prompt = "\n".join(lines)
   print(f"Total characters: {len(prompt)}")
   print(f"Total messages: {sum(len(e.get('original_data', [])) for e in episodes)}")
   
   with open('/tmp/raw_experiment_input.txt', 'w') as f:
       f.write(prompt)
   ```
2. **调用 LLM**：将 `/tmp/raw_experiment_input.txt` 内容作为 system prompt + 10 个问题的 user message，发送给 Claude/GPT。
3. **记录评分**：根据第 3 节的评分标准，逐题评分，填入评估表。
4. **重复 3 次**：用同样 prompt 和 Temperature=0 重复 3 次，取众数结果。

## 7. 实验结论对 Graph DB 路线的影响

| 实验结果 | 对图 DB 路线的影响 | 建议动作 |
|---------|------------------|---------|
| 原始模式 > 预处理模式（场景 A） | 削弱图 DB 价值——预处理管线的必要性都成疑，更不用谈图 DB | 推迟图 DB 迁移，先优化 MemoryGraph + 实验原始模式 |
| 预处理模式 > 原始模式（场景 B） | 支持图 DB 价值——但仅支持"预处理有意义"，不直接支持"需要图 DB" | 继续 Phase A（MemoryGraph 优化），不引入 Neo4j |
| 两者都不好（场景 C） | 两者都无法使用——问题在 LLM 本身，不在存储层 | 暂停所有存储优化，先改善 prompt/few-shot 质量 |

**所有三种场景都不会导向"立即引入 Neo4j"**。因为 Step 0 数据审计已确认 ~44 节点（远小于 10^4 瓶颈线）。
